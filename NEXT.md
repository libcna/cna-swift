## The decision Foundation 23 made

`null` is a value. An exception is not. The two are projected on independent
axes, and all four combinations are legitimate:

```swift
var P: T { get }               // proven non-null, infallible
var P: T? { get }              // proven nullable, infallible
var P: T { get throws }        // proven non-null, fallible
var P: T? { get throws }       // proven nullable, fallible
```

`throws` never stands in for a normal null, and Optional never absorbs a real
failure. A reference return the CIL proves neither way keeps the non-Optional
projection and is **named individually** rather than guessed. Full statement:
`docs/xna-swift-mapping.md`.

Nullability is derived, not judged:
`tools/api_compat/reference/xna40-reference-return-nullability.json` is the
pinned verdict for all 369 public reference-typed return positions,
regenerated by `tools/api_compat/return_nullability.py` from the CIL of the
seven registered assemblies and hash-checked by the verifier as the metadata
contract is. It records only CLR facts and regenerates byte-identically.

## Public signatures changed

None on any complete type. The audit of all 56 reference return positions on
the 118 complete types found **no wrong signature**: 45 are unproven and keep
the non-Optional projection (40 of them `ToString()`, which reaches
`System.String.Format` outside the registered set), 10 are proven non-null and
were already non-Optional, and the one proven-nullable case
(`ResourceCreatedEventArgs.Resource`) was already `Any?`.

Two **expected** shapes were corrected on protected runtime partials, and both
are now measured mismatches rather than invisible differences:

```diff
 // Microsoft.Xna.Framework.GraphicsDeviceManager
-var GraphicsDevice: Graphics.GraphicsDevice { get throws }
+var GraphicsDevice: Graphics.GraphicsDevice? { get }

 // Microsoft.Xna.Framework.Game
-var GraphicsDevice: Graphics.GraphicsDevice { get throws }
+var GraphicsDevice: Graphics.GraphicsDevice? { get throws }
```

Neither implementation was changed. `cna_game_get_graphics_device` returns a
`CNA_Result` and one `CNA_Handle` and defines no success-with-absent case, so
CNA cannot presently tell "XNA has no device yet" from "the native call
failed"; returning nil would mean catching every error and calling it absence,
and making the manager's getter infallible would mean discarding CNA's own
generation and thread-ownership checks. The expected shape is recorded, the
runtime work is not pretended. No CNA ABI symbol was added.

## Recommended next frontier, in value order

### 1. Register a BCL behaviour authority, then decide the collection base

Two decisions, in this order.

**(a) How is an assembly that declares no contract type registered?** The
current gate in `pinned_assembly_audit.py` earns authority by machine-comparing
an assembly's public metadata against every contract entry it declares.
`mscorlib` declares none, so that gate passes vacuously and calibrates nothing.
A BCL authority needs its own calibration rule — for example, reproducing the
public shape of the specific BCL types the binding relies on and pinning that,
the way the XNA contract is pinned.

**(b) How does a CLR class used as a *base* project into Swift?** This is the
question `GameComponentCollection` (base `Collection<IGameComponent>`),
`LaunchParameters` (base `Dictionary<String,String>`), the eight exception
types (base `Exception` / `ExternalException`), the five attribute types (base
`Attribute`) and `MathTypeConverter` (base `ExpandableObjectConverter`) all
share. It is one decision covering 16 still-missing types, and the shape
evidence for the collection half is now in hand:

```text
Collection`1<T>          public Count/Item, Add/Clear/Contains/CopyTo/
                         GetEnumerator/IndexOf/Insert/Remove/RemoveAt,
                         protected Items and the four virtual hooks
                         ClearItems/InsertItem/RemoveItem/SetItem
ReadOnlyCollection`1<T>  public Count/Item, Contains/CopyTo/GetEnumerator/
                         IndexOf, protected Items
```

`.ctor()` allocates a `List<T>`; `.ctor(IList<T>)` wraps the caller's list
**live**. Flattening either to a Swift `Array` would discard both the reference
identity and the live view, so that is not an available answer.

Unblocks, once decided: `GameComponentCollection`, `GraphicsAdapter`,
`Microphone`, `SpriteFont`, `VisualizationData`, `LaunchParameters`, the eight
exception types, the five `ContentSerializer*Attribute` types,
`GameServiceContainer`, `ContentManager` and `MathTypeConverter`.

### 2. `GameComponent` — pure managed, blocked one call deep

Its own IL is entirely managed, but `Dispose(bool)` unregisters the component
from `Game.Components`, which is a `GameComponentCollection`. It follows
frontier 1 immediately and needs no decision of its own.

### 3. CLR abstract class members

`GameWindow` has nine `abstract` public members. Swift has no abstract member,
and projecting one is undecided; every one of those members also needs a real
window system, so this frontier is doubly blocked.

## Reference parameters — checked, not reopened

The selective `optionalReferenceParameters` policy is unchanged and **no
selected entry was found inconsistent**. Every public reference parameter on an
implemented type was checked against its own IL for a normal (non-throwing)
null path; the seven `Equals(object)` cases are already Optional through the
`System.Object` mapping, and `KeyboardState..ctor(Keys[])` proved to treat null
and empty identically, so its non-Optional `[Keys]` loses nothing.

One gap was recorded for the future: `GraphicsDevice.SetRenderTarget`,
`SetRenderTargets`, `SetVertexBuffer` and `SetVertexBuffers` all treat null as
"unbind" — an observable selected operation under the existing rule — and all
are still `MISSING_MEMBER`. Whoever implements them must project those
parameters as Optional. Details:
`docs/foundation-23-parameter-nullability-observations.md`.
