## The decision this session made

Swift has no throwing property setter, and the compiler separately refuses any
`set` beside a getter that is `throws`. Every CLR property is now projected
**per accessor**: the getter keeps property or subscript syntax and gains
`get throws` exactly when the XNA getter is fallible; a setter Swift cannot
express becomes `Set<PropertyName>` carrying the setter's own `throws`.

```swift
public var DopplerScale: Float { get }
public func SetDopplerScale(_ value: Float) throws
```

The writer is the projection of the CLR setter **accessor**, not a new XNA
member — reader and writer are recombined into one source property identity, so
`EXPECTED_SWIFT_MEMBERS` is unchanged at 2887. The `Item`/`SetItem` rule for
indexed properties is the same rule, unchanged. Full statement and the twelve
combinations: `docs/xna-swift-mapping.md`.

Fallibility is derived, not judged:
`tools/api_compat/reference/xna40-accessor-fallibility.json` is the pinned
per-accessor verdict for all 840 public properties, regenerated by
`tools/api_compat/accessor_fallibility.py` from the CIL of the seven registered
assemblies and hash-checked by the verifier as the metadata contract is. It
regenerates byte-identically.

## Public signatures changed

One, on an already-complete type.

```diff
 // Microsoft.Xna.Framework.Graphics.IEffectFog
-var FogColor: Microsoft.Xna.Framework.Vector3 { get set }
+var FogColor: Microsoft.Xna.Framework.Vector3 { get throws }
+func SetFogColor(_ value: Microsoft.Xna.Framework.Vector3) throws
```

`FogEnabled`, `FogStart` and `FogEnd` are unchanged. This was a correctness fix,
not a style change: every registered implementor forwards `FogColor` to
`EffectParameter`, which throws, and Swift rejects a throwing getter as the
witness of a non-throwing requirement — the old requirement could not have been
conformed to by any XNA-shaped effect. Conformers must now be reference types,
because the writer is non-mutating; both in-repo witnesses became `final class`.

`IEffectMatrices` is unchanged. No other complete type's signature moved.

## A defect the new rule exposed, deliberately not fixed

`GraphicsDeviceManager.GraphicsDevice` is `{ get throws }` in Swift while the
pinned getter is a bare `ldfld` — infallible. It is now a measured
`PROPERTY_MAPPING_MISMATCH` instead of an invisible difference, and it is not
corrected, because the CLR getter can return **null**, the Swift return type is
a non-optional class, and CNA has no device to return before one exists. Making
it non-throwing would require fabricating a device or trapping. The real
question is the projection of a nullable CLR reference return — a new undecided
mapping, listed below.

## Why this session stopped

**Every one of the 33 dependency-complete missing types was re-checked
mechanically against the decided mapping table, and each needs a new decision,
a real runtime, real hardware, or a value the CLR does not specify.**

Nine have no undecided BCL type left at all, and every one of those is blocked
by something that cannot be fabricated:

| Type | Blocker |
|---|---|
| `Graphics.EffectAnnotation` | every accessor reads `ID3DXBaseEffect` |
| `Audio.AudioCategory` | `SetVolume`/`Pause`/`Resume`/`Stop` drive the XACT engine |
| `Audio.SoundEffectInstance` | wraps an XACT voice |
| `Media.MediaSource` | `GetAvailableMediaSources` enumerates real device sources |
| `FrameworkDispatcher` | `Update` pumps audio, media and networking |
| `TitleContainer` | `OpenStream` opens real title storage |
| `Input.Mouse`, `Input.Touch.TouchPanel` | real hardware |
| `Audio.RendererDetail` | `GetHashCode` is `_name.GetHashCode() ^ _id.GetHashCode()`, and `System.String.GetHashCode` is unspecified in the CLR — any value would be fabricated |

The other 24 each need a BCL mapping decision this milestone did not make.

`GameComponentCollection` remains deferred and machine-guarded. The
throwing-accessor rule says nothing about its `Collection<IGameComponent>` base,
which is where almost all of its usable surface comes from.

## Recommended next frontier, in value order

Each of these is a **new public API decision**, not an implementation task.
None has a single mapping that already follows from repository policy.

### 1. `System.Exception` / `ExternalException` — 8 types, largest cluster

`InstancePlayLimitException`, `NoAudioHardwareException`,
`NoMicrophoneConnectedException`, `ContentLoadException`, `DeviceLostException`,
`DeviceNotResetException`, `NoSuitableGraphicsDeviceException`,
`StorageDeviceNotConnectedException`. Each declares only constructors: `()`,
`(String)`, `(String, Exception)`, and two also
`(SerializationInfo, StreamingContext)`.

The material question is not the base class, it is that **CNA already has an
error model**: `CNAError` carries the projections of the CLR exceptions the
pinned surface throws. Introducing XNA exception *types* creates a second one.
Plausible, materially different answers: an `open class CNAException: Error`
support base following the `CNAEventArgs` precedent, with the derived types as
Swift classes; folding them into `CNAError` cases and losing type identity; or
`Error`-conforming structs with no shared base, which cannot express
`ExternalException` deriving from `Exception`. The two
`(SerializationInfo, StreamingContext)` constructors project CLR binary
serialization, which has no Swift analogue at all, and would stay
`MISSING_MEMBER` under every option.

### 2. `Collection<T>` / `ReadOnlyCollection<T>` — unblocks 6 types

`GameComponentCollection`, `VisualizationData`, `GraphicsAdapter`, `SpriteFont`,
`Microphone`, `ModelMeshPart`-adjacent surface.

Repository policy covers the collection *interfaces* — `ICollection<T>`,
`IList<T>`, `IEnumerable<T>` map to the concrete XNA members that implement
them, with no automatic Swift `Collection` conformance. It does **not** cover
these two, which are classes whose members a derived XNA type does not declare:
`GameComponentCollection` declares only a constructor, four protected overrides
and two events, and inherits everything usable.

There is an additional, harder blocker specific to this frontier: **there is no
behaviour authority for it.** `Collection<T>` lives in `mscorlib`, which is not
one of the seven registered assemblies, and the XNA-era .NET Framework 4.0
`mscorlib` is not present — only .NET 8 facades and Mono's reimplementation,
neither of which is Microsoft's XNA-era behaviour. Registering a BCL authority
is itself a provenance decision the repository has always made deliberately.
Flattening to Swift `Array` is not an option: it discards reference identity and
the live view.

### 3. Nullable CLR reference returns

Surfaced by `GraphicsDeviceManager.GraphicsDevice` above. A CLR reference return
is nullable; the Swift projection is currently non-optional, and CNA has been
substituting `throws` for "no value". Deciding this properly (`T?` vs `throws`
vs a documented non-null contract) affects many still-missing members.

### 4. `System.Attribute` — 5 `ContentSerializer*Attribute` types

Swift has its own attribute system and no way to attach these; the content
pipeline that reads them is not implemented. A `CNAAttribute` support base is
plausible, and so is "CLR attribute metadata has no Swift counterpart".

### 5. `System.Type` / `IServiceProvider` (`GameServiceContainer`), then `Dictionary<K,V>` (`LaunchParameters`), then `System.ComponentModel.TypeConverter` (`MathTypeConverter`)

`System.Type` has no faithful Swift counterpart; a Swift metatype is not a CLR
`Type`. `Dictionary<K,V>` as a *base class* has the same missing-authority
problem as `Collection<T>`.
